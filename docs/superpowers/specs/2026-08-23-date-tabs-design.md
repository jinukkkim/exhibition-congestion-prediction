# 날짜별 차트 조회 설계

## 배경

두 관 페이지의 차트가 모두 "오늘"에 고정되어 있다. 국립중앙박물관 페이지는
`PredictionChart`가 오늘 하루의 예상 곡선만 그리고, MMCA 페이지는 전시실 카드가
오늘 실선과 지난주 같은 요일 회색선을 겹쳐 보여준다. 어느 쪽도 "다음 토요일은
얼마나 붐빌까"에 답하지 못한다.

방문 계획을 세우는 사람이 앞으로의 날짜를 골라 그 날의 추이를 볼 수 있게 한다.
참고한 화면은 footlab의 혼잡도 페이지로, 오늘부터 6일 뒤까지의 날짜 탭을 두고
선택한 날의 예상 추이를 보여준다.

## 두 관의 데이터 의미가 다르다

| | 탭이 보여주는 것 | 출처 | 백엔드 변경 |
| --- | --- | --- | --- |
| 국립중앙박물관 | 그 날짜의 **예상** 곡선 (baseline + model) | 배치가 계산해 Redis에 적재 | 필요 |
| MMCA 3관 | 그 날짜 **−7일의 실제** 곡선 | `/mmca/daily?venue=&date=` (기존) | 없음 |

MMCA에는 예측 모델이 없다. 수집하는 값이 전시실별 혼잡도 등급뿐이고 인원수가
없어서 회귀 모델의 목표변수가 존재하지 않는다. 그래서 현재 가진 최선의 대리값인
"지난주 같은 요일의 실제 기록"을 보여준다 — 이미 회색 비교선으로 쓰고 있는 것을
임의 날짜로 일반화하는 것이다.

**미래 탭의 선을 "예상"이라 적지 않는다.** MMCA 미래 탭은 그 선이 실제로 무엇인지
그대로 적는다 (`8/22(토) 실제`) 그리고 카드에 한 줄로 이유를 남긴다
(`예상 대신 지난주 같은 요일의 실제 기록`). 예측이 생기면 선이 추가되고 문구가
바뀐다.

## 미래 예측이 이미 계산 가능한 이유

`backend/app/prediction/model.py`의 피처가 `[weekday, hour, is_holiday]` 셋뿐이다.
날씨나 직전 관측값처럼 시점에 의존하는 피처가 없어서, 임의의 미래 시각에 대해
그대로 예측할 수 있다. `baseline.py`도 `(weekday, hour)` 키라 마찬가지다.

`run_daily_batch`는 이미 `today.weekday()`로 24시간 커브 하나를 만든다. 이 설계는
그 루프를 7일로 넓히는 것이 전부다.

## 탭 기간: 오늘 + 6일

7일이 **모델 구조상 중복이 없는 최대치**다. 피처가 요일과 공휴일 여부뿐이므로,
7일을 넘기면 다음 주 월요일 곡선이 이번 주 월요일과 완전히 동일해진다. 탭을
늘리는 것이 정보를 내지 않고 사용자를 오해하게 만든다.

공휴일은 피처에 있으므로 공휴일인 월요일은 평일 월요일과 다른 곡선이 나온다.

## 백엔드 설계

### 접근 선택

배치가 7일 커브를 미리 계산해 Redis 페이로드에 담고, 라우트가 그대로 서빙한다.
7 × 24 = 168 포인트로 페이로드가 작고, 모델을 직렬화해 보관할 필요가 없어
기존 "배치 계산 → Redis → 라우트 서빙" 구조가 그대로 유지된다.

대안으로 모델을 joblib로 저장해 요청 시 임의 날짜를 예측하는 방법을 검토했다.
날짜 제약이 없어지지만 모델 직렬화·sklearn 버전 호환·라우트 콜드스타트가 붙는다.
숫자 168개를 얻기 위한 비용으로 과하다.

라우트가 요청 시 baseline만 다시 계산하는 방법도 검토했다. baseline은 DB 평균이라
라우트에서 가능하지만 model은 불가능해서 두 시리즈 중 하나만 미래로 확장되는
반쪽이 된다.

### 응답 페이로드

`GET /congestion/prediction`에 `days`를 추가한다.

```json
{
  "status": "ready",
  "baseline_mae": 151.5,
  "model_mae": 146.7,
  "curve": [{ "hour": 0, "baseline": 800.0, "model": 812.3 }, "…24개"],
  "days": [
    {
      "date": "2026-08-23",
      "is_holiday": false,
      "curve": [{ "hour": 0, "baseline": 800.0, "model": 812.3 }, "…24개"]
    },
    "…오늘 + 6일, 최대 7개"
  ]
}
```

`curve`를 남겨 둔다. `deploy/deploy.sh`는 백엔드를 먼저 재시작하고 프론트 번들을
마지막에 발행하므로 "구 프론트 + 신 백엔드" 구간이 존재하고, 그 배포 순서의
안전성이 하위 호환에 기대고 있다. 필드를 지우면 그 구간에 예측 카드가 빈 차트가
된다. `curve`는 `days[0]`(오늘)의 커브와 같은 값이다.

`status`가 `collecting`일 때는 `days`를 넣지 않는다 (지금 `curve`를 넣지 않는 것과
같다).

### 배치 변경

`backend/app/prediction/batch.py`의 커브 생성부를 7일 루프로 바꾼다. 날짜별
`is_holiday`는 `model.py`가 이미 피처로 쓰는 `_KR_HOLIDAYS`를 그대로 쓴다 —
판정 출처가 갈리지 않게 한다.

MAE 계산, 학습/평가 분할, `MIN_DAYS_REQUIRED = 14` 게이트는 손대지 않는다.

### 자정부터 03:00까지의 창

배치는 `scheduler.py`의 `CronTrigger(hour=3, minute=0, timezone=Asia/Seoul)`로
하루 한 번 돈다. 따라서 자정부터 03:00 사이에는 저장된 첫 커브의 날짜가 "어제"다.

라우트가 `date >= 오늘(KST)`인 항목만 내려보낸다. 그 3시간 동안 탭은 7개가 아니라
6개가 된다. 배치가 실패한 날도 탭이 하루씩 줄어들어 눈에 보이는 열화가 되고,
틀린 날짜를 오늘로 제시하는 일은 생기지 않는다.

`cache.py`의 `PREDICTION_TTL_SECONDS = 86400`이므로 배치가 하루 넘게 실패하면
페이로드 자체가 사라지고 응답이 `{"status": "collecting", "days_collected": 0}`으로
떨어진다. 이 동작은 이 설계에서 바꾸지 않는다.

## 프론트 설계

### `components/DateTabs.tsx` (신규)

두 페이지가 공유하는 탭 스트립.

```ts
export function DateTabs({
  dates,          // "YYYY-MM-DD"[] — 오늘부터 순서대로
  selected,
  onSelect,
}: {
  dates: string[];
  selected: string;
  onSelect: (date: string) => void;
}): JSX.Element;
```

첫 항목은 `오늘 (일)`, 나머지는 `월 8/24` 형태. 요일 이름은 `lib/date.ts`의
`monthDayWeekday`가 이미 쓰는 `WEEKDAY_KO` 배열을 재사용한다.

접근성: `role="tablist"` / `role="tab"` + `aria-selected`. 선택된 탭에만
`aria-selected="true"`를 둔다.

날짜 목록을 만드는 것도 `lib/date.ts`에 둔다 — `shiftDate`가 이미 있으므로
`upcomingDates(today, 7)` 한 함수로 충분하다.

### `PredictionChart` (국립중앙박물관)

카드 상단에 `DateTabs`를 두고, 선택된 날짜의 커브를 기존 곡선 렌더에 넘긴다.
곡선 렌더 로직 자체는 바꾸지 않는다.

`days`가 없으면(구 백엔드 응답, 또는 `collecting`) 탭을 그리지 않고 지금처럼
`curve`만 그린다.

선택된 날짜가 응답에서 사라진 경우(자정을 넘겨 폴링이 갱신된 경우) 첫 항목으로
되돌린다 — 없는 날짜를 선택한 상태로 빈 차트를 그리지 않는다.

### `MmcaPage`

전시실 그리드 위에 `DateTabs`를 둔다. 카드마다 두지 않는 이유는 `daily` fetch가
관 단위 한 건이라, 서울관에서 같은 컨트롤이 7~8개로 복제되고 실패·선택 상태를
여러 곳에서 유지해야 하기 때문이다 (추이 실패 안내를 관 단위로 둔 것과 같은 이유).

데이터 배선:

- **오늘 탭** — 지금과 동일. 오늘 실선 + `오늘 − 7일` 회색선
- **미래 날짜 D 탭** — `D − 7`의 실제 곡선 한 줄. 오늘 실선은 그리지 않는다

`D − 7`은 D가 오늘~오늘+6이므로 항상 어제~7일 전이고, 수집 시작일(2026-07-17)보다
뒤다. 따라서 데이터 없는 날짜를 요청하는 경우는 생기지 않는다.

기존 `lastWeekPoll`이 이미 `오늘 − 7일`을 받고 있으므로, 그 fetch의 날짜 인자를
`선택 날짜 − 7일`로 일반화하면 된다. `stopWhenLoaded`는 유지한다 — 지나간 날의
확정 데이터라는 성질이 그대로다. 선택이 바뀌면 `deps`가 바뀌어 다시 받는다.

`MmcaRoomChartCard`는 오늘 실선을 그릴지 여부를 prop으로 받는다. 미래 탭에서
"오늘 데이터"를 함께 그리면 서로 다른 날짜의 두 선이 한 차트에 겹쳐 무엇을 보는지
알 수 없게 된다.

## 단계

공유 컴포넌트를 더 복잡한 쪽에서 먼저 뽑고 재사용한다. 각 단계가 독립적으로
동작하는 소프트웨어를 만들고, PR을 나눈다.

**1단계 — 국립중앙박물관 예측 탭**
`batch.py` 7일 루프, 라우트 필터, `lib/date.ts`의 `upcomingDates`,
`DateTabs`, `PredictionChart` 배선.

**2단계 — MMCA 과거 대리값 탭**
`DateTabs` 재사용, `MmcaPage`의 선택 날짜 배선, `MmcaRoomChartCard`의 오늘 실선
prop, 미래 탭 문구.

## 알려진 한계

- **7일을 넘길 수 없다.** 피처가 요일과 공휴일 여부뿐이라 그 이상은 같은 곡선의
  반복이다. 날짜별로 다른 예측을 하려면 날씨 예보 같은 시점 의존 피처가 필요하고,
  `ForecastWeather` 테이블에 예보가 이미 쌓이고 있으므로 재료는 있다 — 별건이다
- **MMCA 탭은 예측이 아니다.** 지난주 같은 요일의 실제 기록이며, 화면에 그대로
  적는다. MMCA 예측은 인원수 같은 연속형 목표변수가 없어 현재 구조로는 불가능하다
- **모델이 baseline을 거의 이기지 못한다.** 프로덕션 실측 baseline MAE 151.5 대
  model MAE 146.7. 날짜 탭은 이 정확도를 개선하지 않는다 — 있는 예측을 날짜별로
  보여주는 것뿐이다
- 자정부터 03:00까지 탭이 6개다 (위 "자정부터 03:00까지의 창")

## 동시 작업과 겹치는 지점

차트 아래 로그 표(`DailyLogTable`, `MmcaDailyLogTable`)를 별 페이지로 옮기는
작업이 병행 중이다. 그 작업과 이 설계는 `NationalMuseumPage.tsx`와
`MmcaPage.tsx`의 섹션 목록을 함께 건드리므로 그 JSX에서 충돌이 날 수 있다.

이 설계는 표를 건드리지 않는다. 표가 옮겨가면 페이지에 날짜 컨트롤이 하나만
남으므로, 탭과 표의 날짜 선택기가 한 화면에 공존하는 문제도 자연히 사라진다.
